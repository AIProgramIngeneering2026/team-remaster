# Требования

Участник во всех сценариях — **клиент API**: человек или другой сервис, который обращается к нашему REST API.
Поддерживаемые форматы документов — PDF, DOCX, TXT; максимальный размер файла — 20 МБ.
Все ошибки возвращаются в едином формате `{code, message, details}`.

## Сценарий 1. Извлечение текста из документа (основной)

**Цель:** получить текст документа, не открывая его вручную.

**Основной поток:**
1. Клиент загружает документ: `POST /documents` → получает `document_id`.
2. Клиент создаёт задание: `POST /jobs` с операцией `extract_text`, `document_id` и заголовком `Idempotency-Key`.
3. Сервис создаёт Job в состоянии `uploaded` и сразу отвечает `201` с `job_id`.
4. Сервис проверяет документ, переводит Job в `queued`, затем в `processing`.
5. Процессор `TextExtractor` извлекает текст, Job переходит в `processed`.
6. Клиент запрашивает `GET /jobs/{id}` и получает статус `processed` и текст в результате.

**Критерии приёмки:**
- **Дано** загружен корректный PDF, DOCX или TXT до 20 МБ, **когда** клиент создаёт задание `extract_text`,
  **тогда** задание завершается в `processed`, а в результате — извлечённый текст.
- **Дано** задание уже создано с ключом `Idempotency-Key: abc`, **когда** клиент повторяет `POST /jobs`
  с тем же ключом и тем же телом, **тогда** сервис возвращает `200` с прежним `job_id`, новое задание не создаётся.
- **Дано** задание создано с ключом `Idempotency-Key: abc`, **когда** клиент отправляет `POST /jobs`
  с тем же ключом, но другим телом, **тогда** сервис отвечает `409`, `code = "idempotency_conflict"`,
  новое задание не создаётся. Ключ хранится 24 часа.
- **Дано** задание в `processing`, **когда** клиент запрашивает `GET /jobs/{id}`,
  **тогда** он получает текущий статус без результата.

## Сценарий 2. Подсчёт статистики документа

**Цель:** быстро узнать объём документа.

**Основной поток:**
1. Клиент загружает документ (как в сценарии 1).
2. Клиент создаёт задание `POST /jobs` с операцией `stats`.
3. Процессор `StatsProcessor` считает число слов, символов, абзацев и 10 самых частых слов.
4. Job переходит в `processed`, клиент получает статистику через `GET /jobs/{id}`.

**Критерии приёмки:**
- **Дано** корректный документ с текстом, **когда** выполняется задание `stats`,
  **тогда** результат содержит поля `words`, `chars`, `paragraphs`, `top_words`.
- **Дано** пустой документ (без текста), **когда** выполняется задание `stats`,
  **тогда** задание завершается в `processed` с нулевыми значениями, а не ошибкой.

## Сценарий 3 (ошибочный). Неподдерживаемый или слишком большой документ

**Цель:** система не должна пытаться обработать то, что не умеет.

**Поток:**
1. Клиент загружает файл `.exe`, или PDF размером 50 МБ, или файл с расширением `.pdf`, внутри которого не PDF.
2. Клиент создаёт задание на этот документ.
3. Сервис при проверке документа переводит Job из `uploaded` в `rejected` с причиной.

**Критерии приёмки:**
- **Дано** файл неподдерживаемого формата, **когда** клиент создаёт задание,
  **тогда** Job переходит в `rejected`, `error.code = "unsupported_format"`.
- **Дано** файл больше 20 МБ, **когда** клиент его загружает,
  **тогда** сервис отвечает `413` с кодом `file_too_large`, документ не сохраняется.
- **Дано** файл с расширением `.pdf`, но содержимое не PDF (неверная сигнатура), **когда** сервис
  проверяет документ, **тогда** Job переходит из `uploaded` в `rejected`, `error.code = "corrupted_file"`.
- **Дано** файл с верной сигнатурой, но обрезанный, **когда** задание доходит до обработки,
  **тогда** Job переходит в `failed`, `error.code = "parse_error"`, сервис продолжает работать.

## Сценарий 4 (ошибочный). Неизвестная операция или неверные параметры

**Цель:** клиент должен понять, что именно не так в его запросе.

**Поток:**
1. Клиент отправляет `POST /jobs` с операцией, которой нет, или без обязательного поля.
2. Сервис отклоняет запрос до создания задания.

**Критерии приёмки:**
- **Дано** запрос с `"operation": "dance"`, **когда** клиент отправляет `POST /jobs`,
  **тогда** сервис отвечает `400`, `code = "unknown_operation"`, задание не создаётся.
- **Дано** запрос без `document_id` или с `document_id` не строкой, **когда** клиент отправляет `POST /jobs`,
  **тогда** сервис отвечает `400`, `code = "invalid_params"`, `details.field = "document_id"`.
- **Дано** `document_id`, которого нет, **когда** клиент отправляет `POST /jobs`,
  **тогда** сервис отвечает `404`, `code = "document_not_found"`, задание не создаётся.

## Сценарий 5 (ошибочный). Сервис перевода недоступен

**Цель:** отказ внешнего сервиса не должен вешать задание и ломать остальные операции.

**Поток:**
1. Клиент создаёт задание `translate`.
2. Адаптер `TranslationClient` обращается к LibreTranslate, сервис не отвечает или отвечает мусором.
3. Если сервис не ответил или вернул ошибку 5xx, адаптер повторяет запрос (до 3 попыток, таймаут 10 с на каждую).
   На некорректный ответ (не JSON, нет поля с переводом) повтор не делается.
4. После неудачных попыток Job переходит в `failed`.

**Критерии приёмки:**
- **Дано** сервис перевода не отвечает, **когда** выполняется задание `translate`,
  **тогда** после 3 попыток Job переходит в `failed`, `error.code = "translation_unavailable"`.
- **Дано** сервис перевода вернул не JSON или ответ без поля с переводом, **когда** выполняется задание,
  **тогда** Job переходит в `failed`, `error.code = "translation_bad_response"`.
- **Дано** сервис перевода недоступен, **когда** клиент создаёт задания `extract_text` и `stats`,
  **тогда** они выполняются как обычно.

## Сценарий 6. Отмена задания

**Цель:** клиент передумал и хочет отменить задание, которое ещё не начало выполняться.

**Основной поток:**
1. Клиент создал задание (как в сценарии 1) и получил `job_id`.
2. Клиент отправляет `POST /jobs/{id}/cancel`.
3. Сервис проверяет текущее состояние задания: отмена возможна только из `uploaded` и `queued`.
4. Задание переходит в `cancelled`, клиент получает `200` и новый статус.
5. Процессор это задание больше не берёт в работу.

**Критерии приёмки:**
- **Дано** задание в `uploaded` или `queued`, **когда** клиент отправляет `POST /jobs/{id}/cancel`,
  **тогда** сервис отвечает `200`, задание переходит в `cancelled` и не выполняется.
- **Дано** задание в `processing`, **когда** клиент отправляет `POST /jobs/{id}/cancel`,
  **тогда** сервис отвечает `409`, `code = "invalid_transition"`, в `details.status` — текущее состояние,
  задание продолжает выполняться.
- **Дано** задание в конечном состоянии `processed`, `rejected` или `failed`, **когда** клиент отправляет отмену,
  **тогда** сервис отвечает `409`, `code = "invalid_transition"`, результат задания не меняется.
- **Дано** задание уже в `cancelled`, **когда** клиент повторяет отмену,
  **тогда** сервис отвечает `200` без изменений (повторная отмена безопасна).
- **Дано** задания с таким `id` нет, **когда** клиент отправляет отмену,
  **тогда** сервис отвечает `404`, `code = "job_not_found"`.

## Жизненный цикл Job

Состояния:
- `uploaded` — задание создано, документ ещё не проверен;
- `queued` — документ проверен, задание ждёт выполнения;
- `processing` — процессор выполняет задание;
- `processed` — успешно завершено, есть результат (конечное);
- `rejected` — документ не прошёл проверку (конечное);
- `failed` — ошибка при выполнении (конечное);
- `cancelled` — отменено клиентом (конечное).

Разрешённые переходы:
- `uploaded → queued` — документ прошёл проверку;
- `uploaded → rejected` — документ не прошёл проверку;
- `uploaded → cancelled` — отмена клиентом;
- `queued → processing` — задание взято в работу;
- `queued → cancelled` — отмена клиентом;
- `processing → processed` — успех;
- `processing → failed` — ошибка процессора или внешнего сервиса.

Все остальные переходы запрещены. Попытка такого перехода отклоняется ошибкой `invalid_transition`
(`409`), состояние задания не меняется. Например:
- `processing → cancelled` — отменить выполняющееся задание нельзя;
- `processed → processing` — завершённое задание нельзя запустить снова, повтор — только новым заданием.

Переход выполняется атомарно и только если текущее состояние совпадает с ожидаемым. Если два перехода
пришли одновременно (например, отмена клиентом и взятие в работу воркером), выполняется первый, второй
получает `409 invalid_transition` с актуальным состоянием. Повторная отмена уже отменённого задания
возвращает `200` без изменений.
