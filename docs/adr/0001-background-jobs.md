# ADR-0001. Задания выполняются в фоне, а не в запросе

- **Дата:** 2026-11-14
- **Статус:** принято
- **Авторы:** ВасиновичСВ, КопытовЕА

## Контекст

Клиент создаёт задание запросом `POST /jobs`. Обработка документа длится по-разному:
подсчёт статистики TXT - доли секунды, извлечение текста из большого PDF или конвертация - секунды и десятки секунд,
перевод зависит от внешнего сервиса LibreTranslate, который может отвечать медленно (таймаут 10 с,
до 3 попыток - больше 30 секунд в худшем случае).

Ограничения:
- HTTP-клиенты и прокси обычно обрывают запрос через 30–60 секунд - клиент получит таймаут,
  хотя работа могла завершиться (карта К2 «Ответ потерялся»);
- у задания есть жизненный цикл со статусами и отменой - его нужно где-то наблюдать между запросами;
- брокеры сообщений (Kafka, RabbitMQ) курс не оценивает, а команда из двух человек;
- ядро не должно зависеть от веб-фреймворка.

## Решение

`POST /jobs` только создаёт задание в состоянии `uploaded`, сохраняет его и сразу отвечает `201` с `job_id`.
Выполняет задание **Dispatcher** - фоновый обработчик в том же процессе, что и HTTP API:
он берёт задания из хранилища, ведёт их по состояниям и вызывает процессор.
Клиент узнаёт результат через `GET /jobs/{id}`.

При старте сервиса Dispatcher переводит задания, оставшиеся в `processing`, в `failed`
с `error.code = "interrupted"` - после перезапуска их процессоры уже не работают.

## Рассмотренные альтернативы

| Вариант | Почему не выбрали |
|---|---|
| **Синхронно в запросе**: `POST /jobs` ждёт окончания обработки и возвращает результат | Долгие операции упираются в таймауты HTTP; при обрыве соединения клиент не знает, выполнено ли задание; отмена теряет смысл - к моменту отмены всё уже идёт внутри запроса; статусы `queued` и `processing` никто не увидит |
| **Отдельный процесс-воркер и брокер сообщений** (Celery + Redis/RabbitMQ) | Лишний сервис в `docker compose` и ещё одна точка отказа; для нагрузки учебного проекта избыточно; брокеры не оцениваются; два процесса для запуска и отладки вместо одного |
| **Синхронно для быстрых операций, в фоне для долгих** | Два разных пути выполнения - вдвое больше кода и тестов; клиенту приходится знать, какая операция какая; граница «быстрая/долгая» зависит от размера файла |

## Цена решения

- Клиенту нужен второй запрос (или опрос `GET /jobs/{id}`), чтобы получить результат даже для быстрых операций.
- Обработчик живёт в одном процессе с API: тяжёлая обработка конкурирует с HTTP за ресурсы,
  падение процесса останавливает и API, и обработку.
- Нужен механизм восстановления после перезапуска (`processing → failed`, `interrupted`).
- Нельзя масштабировать обработку отдельно от API, не меняя архитектуру.

## Условия пересмотра

Пересматриваем, если:
- обработка начнёт заметно замедлять ответы API (например, `GET /jobs/{id}` дольше 1 с под нагрузкой);
- понадобится запускать несколько экземпляров сервиса - тогда нужна общая очередь и защита от двойного взятия задания;
- во втором семестре вызов LLM окажется настолько долгим и дорогим, что потребуется отдельный воркер с собственными лимитами.
