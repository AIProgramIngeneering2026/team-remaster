# ADR-0002. Авторизация пользователей — вне границ системы

- **Дата:** 2026-11-14
- **Статус:** принято
- **Авторы:** ВасиновичСВ, КопытовЕА

## Контекст

В практике 1 модель-атакующий нашла дыру: клиент может создать задание по чужому `document_id`
или прочитать чужое задание по `job_id` (раздел «Что предложил ИИ» в [requirements.md](../requirements.md)).
Ту же ситуацию проверяет карта К8 «Чужой или несуществующий id». Мы пообещали зафиксировать решение в ADR.

Ограничения:
- в README авторизация уже записана в «Что не входит»;
- курс не оценивает пользовательский интерфейс и не требует учётных записей; реальные персональные данные
  в проекте — признак слишком сложной темы (`tasks/project.md`);
- команда из двух человек, а впереди обязательные пункты: хранилище, внешний сервис, тесты, диагностика;
- идентификаторы заданий и документов мы генерируем сами.

## Решение

Сервис **не различает клиентов**: нет учётных записей, токенов и проверки владельца.
Он рассчитан на **доверенную среду** — внутреннюю сеть или одного клиента-сервиса.

Чтобы снизить риск угадывания чужих объектов:
- `job_id` и `document_id` — случайные UUID4, а не последовательные номера;
- несуществующий `job_id` → `404 job_not_found`, несуществующий `document_id` → `404 document_not_found`,
  задание при этом не создаётся;
- в ответах и логах нет содержимого чужих документов, кроме результата запрошенного задания.

## Рассмотренные альтернативы

| Вариант | Почему не выбрали |
|---|---|
| **API-ключи клиентов**: заголовок `Authorization: Bearer <ключ>`, у каждого задания и документа владелец | Нужно хранить ключи, выдавать их, проверять владельца во всех операциях и тестировать каждую — заметный объём работы при команде из двух человек, а курс это не оценивает. Самая вероятная альтернатива при пересмотре |
| **Полноценные пользователи** (регистрация, пароли, OAuth) | Персональные данные и безопасность паролей — признак слишком сложной темы; без интерфейса регистрация не имеет смысла |
| **Ограничение доступа на уровне сети** (reverse proxy с базовой авторизацией) | Задача развёртывания, а не сервиса; деплой в курсе не оценивается. Не мешает нашему решению и может быть добавлено снаружи |

## Цена решения

- Любой, кто знает `job_id`, видит статус и результат задания и может его отменить (К8 сознательно не закрыта).
- Сервис нельзя выставлять в открытый интернет без внешней защиты.
- Ключ идемпотентности общий для всех клиентов: два клиента с одинаковым `Idempotency-Key` помешают друг другу.
- Добавить владельца позже — миграция БД и правка всех операций API.

## Условия пересмотра

Пересматриваем, если:
- сервисом начнут пользоваться несколько независимых клиентов или он станет доступен вне доверенной сети;
- в документах появятся данные, которые нельзя показывать другим клиентам;
- во втором семестре вызовы LLM начнут стоить денег — тогда понадобится учёт и лимиты по клиенту,
  а значит, API-ключи.
